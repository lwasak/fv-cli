# Decisions

These are the design decisions behind fv v1. They started as a plan, and this page records what was **actually built**: where the code differs from the plan, the entry says so ("Built:"). Where the plan and the code disagree, the code wins.

"Open" at the end lists what v1 does not cover or could not verify.

## Scope and parties

- **D1.** **GUS BIR1 is deferred.** The White List and VIES are the only registries. *Built:* a NIP the White List does not know ("not registered") exits 2, unless the config gives **both** `name` and `address` for that party: then the party is invoiced from the config (provenance `config`, `statusVat` shown as `Niezarejestrowany`) and fv warns that it is not on the VAT White List. The result is not cached, so the next lookup asks the White List again. This does not apply to the seller or to VIES. Apart from that, the `name` and `address` overrides fill in what a registry **has no value for** (VIES often returns `---`) and replace registry values; without such a value fv exits 2 and names the key to set. A buyer registered but not an active VAT payer is accepted with a warning.
- **D10.** **`0` and `np` stay unsupported.** Foreign currency is allowed only with the Polish rates 23, 8, 5 and `zw`. `np` and `0` are rejected with a message that explains reverse charge is out of v1.
- **D20.** **Registries always use the production White List and VIES hosts**, whatever the KSeF environment. They are public and read-only and hold real data; the test copies hold synthetic data. The URLs are fixed in code.
- **D21.** **The White List is queried with `date` = the earlier of the issue date and today (Europe/Warsaw).** Counters and dates use Europe/Warsaw; the program embeds the time zone database, so this works on Windows too.
- **D22.** **Quota.** A call is non-essential only when it comes from `fv party refresh`. From 90 calls per day, non-essential calls are refused. `fv party add` and invoice-time lookups are essential and fv does not refuse them (MF's own limit of 100 still applies).
- **D23.** **Cache freshness for an invoice.** The buyer is fetched again when the entry is older than 24 hours or was fetched for another query date. The seller is fetched again when the entry is older than `registry.cache_ttl` days (default 30). On a network or quota failure a stale entry is used with a warning; with no cache entry fv exits 2.
- **D24.** **`fv party add`** fetches first and writes the config only on success. It appends a `[parties.<alias>]` block as text, so your comments survive, then reloads the config and restores the old file on failure. Alias format: `^[a-z0-9][a-z0-9_-]{0,31}$`.

## Numbering and archive

- **D2.** **A draft reserves its number** at `fv issue`. `fv discard <number>` releases the number if it is the latest in its counter (the folder is deleted), otherwise marks it `void-draft`. Rejected invoices can be discarded the same way, except a rejected duplicate (KSeF 440), which is always voided because its number is used in KSeF.
- **D3.** **State order is `reserved → draft → sending → accepted | rejected | unknown`.** `reserved` is the short window between taking the number and writing `invoice.xml`. `unknown → draft` is allowed only when KSeF provably never received the invoice (see 26).
- **D4.** **A persisted `sending` state counts as `unknown`** on the next run, since a crash cannot write `unknown`. `fv send` refuses both; `fv status` resolves both.
- **D5.** **Numbering syntax stays the validated one:** `{YYYY} {YY} {MM} {DD} {SEQ} {SEQ:n}`. The default pattern is `FV/{YYYY}/{MM}/{SEQ:3}`.
- **D6.** **New key `numbering.reset`** (`monthly | yearly | never`). When unset it is derived from the pattern. Validation refuses a reset whose period is not in the pattern, so a reset can never produce duplicate numbers. *Built:* a pattern with `{MM}` but no year token derives `never` (not `monthly`), because months of different years would repeat numbers.
- **D7.** **Counter key = environment + period** (`2026-10`, `2026` or `all`), stored in `<data>/state.json`. The period comes from the issue date.
- **D8.** **`state.json` is locked with an OS lock** on `<data>/state.lock` (flock on Unix, LockFileEx on Windows), waiting up to 10 seconds. The lock is released automatically when the process ends, so there are no stale lock files.
- **D34.** **`fv list` with no `--env`** lists all environments. It reads the global `--env` flag directly, not the config default.
- **D33.** **`fv show` renders from `meta.json`**, which carries a snapshot of lines and parties. `--xml` prints the stored bytes exactly, after checking their SHA-256 against `meta.json`.

## Sending and safeguards

- **D9.** **Prod confirmation: the user types `PRODUCTION`** at a terminal prompt, shown in red. `--yes` never skips it and prints a notice saying so. *Built:* with no terminal and no injected confirmation, a send aborts with exit code 10 on **every** environment; on TEST and DEMO `--yes` is the way to send from a script.
- **D25.** **The UPO is fetched from the API path** `/sessions/{ref}/invoices/{invRef}/upo` (Accept `application/xml`). fv never follows the `upoDownloadUrl`, because URLs stay fixed in code.
- **D26.** **`fv status` without an invoice reference** (the POST answer was lost): fv lists the session's invoices and matches the invoice hash. If there is no match and the session is closed (status 170, 200, 415, 440 or 445) or past its validity, **and** KSeF states an invoice count of 0, the state goes `unknown → draft` (proven not received). A session answer that lacks the status or the count proves nothing and leaves the invoice `unknown`. Otherwise it stays `unknown`.
- **D27.** **POST outcomes.** A 4xx answer with a KSeF body means `rejected` (not accepted, so not in KSeF). A transport error, timeout or 5xx means `unknown`. Invoice status 440 (duplicate) means `rejected`, and the original KSeF number is printed. *Built:* the 440 is stored with a duplicate marker and the original KSeF number (`ksef.duplicate`, `ksef.originalKsefNumber`, `ksef.originalSessionRef` in meta.json); `fv show` and `fv status` print it, and `fv discard` only voids such an invoice, it never releases the number (KSeF treats seller NIP + invoice kind + number as the duplicate key, so a reused number would be refused again). fv also keeps every session an invoice was sent in (`sentSessions`, which survives an `unknown → draft`). When the 440 names one of those sessions as the original, the invoice in KSeF is this very invoice: fv finds it there by its hash and records it as `accepted` with its KSeF number and UPO, instead of `rejected`. POSTs are never retried; GETs are retried (up to 3 times, honouring `Retry-After`, capped at 30 seconds) on 429. *Built:* only a 4xx that is about the **invoice** is `rejected`. A POST answered **401, 403 or 429**, or with a session-level exception code (**21155** invoice limit of the session, **21173** no such session, **21180** session status does not allow sending, **21184** session temporarily unavailable), is a refusal of the caller or the session, not of the invoice: KSeF stored nothing, so the draft goes back to `draft` (exit 1) instead of `rejected`. The rule and the code list are in `ksef.RefusedForSession`.
- **D28.** **The send poll budget is 120 seconds** (backoff 1, 2, 4, 4 seconds ...). When it runs out the state becomes `unknown` and fv exits 5.
- **D29.** **fv refuses to send** when the issue date is later than today (Warsaw), because KSeF rejects it. Dry-run drafts may be future-dated.
- **D36.** **The AES session key** (key and IV) is registered with the redactor and zeroed after the session closes.
- **D37.** **Exit codes live in their own package**, so packages can tag errors without importing the command layer: 2 registry, 4 rejected, 5 unknown, 10 aborted. Auth (3) keeps its existing mapping. See [Exit codes](exit-codes.md).
- **D35.** **The secrets fallback** applies only when the keyring service itself is unavailable (no platform support, no D-Bus or Secret Service). Other keyring errors still fail without a fallback. *Not covered:* `fv init` stores the passphrase with the same keyring, so it cannot import a certificate on such a machine. *Built:* it checks the keyring first and stops before reading or copying any file, with a message that explains the `FV_SECRET_KSEF_<ENV>_<NIP>` variable and the copy-the-folder workaround; the passphrase is never written to a file (see Open).

## The invoice

- **D11.** **NBP tax point** is the sale date when there is one, else the issue date. Per art. 31a ust. 2, when the invoice is issued before the sale date, the issue date is used. The rate is the table A mid of the last business day before the tax point: start at tax point minus 1 day and walk back on 404, at most 10 days. fv never walks back past an unpublished table: if tax point minus 1 is after today, or is today and NBP answers 404 for today's table (published around noon), fv fails with "rate not yet published" (exit 1) and the user issues later or sets `--sale-date`/`--issue-date`. Walk-back applies only to days before today. Side effect: when today is itself a non-business day and the tax point is tomorrow, fv also refuses; set the dates explicitly.
- **D12.** **Buyer flags** (checked in the XSD): `Podmiot2/JST` and `GV` are mandatory, 1 = yes and 2 = no. Ordinary B2B buyers get `JST=2`, `GV=2`.
- **D13.** **Adnotacje** (checked in the XSD): every child is mandatory, in order: `P_16=2, P_17=2, P_18=2, P_18A=2`; `Zwolnienie` is `{P_19N=1}`, or for `zw` `{P_19=1, P_19A=<basis>}`; then `NoweSrodkiTransportu{P_22N=1}`, `P_23=2`, `PMarzy{P_PMarzyN=1}`. Cash accounting and split payment are not supported in v1. *Built:* the preview warns when the gross is 15 000 PLN or more (PLN invoices) that split payment may be mandatory for Annex 15 goods and services.
- **D14.** **`zw` basis** goes in `P_19A` (the statutory provision) from `exemption_basis` (defaults or party). `zw` without a basis is a usage error (exit 1). `P_19B` and `P_19C` are not used.
- **D15.** **Schema validation.** There is no pipeline here, so xmllint validation is a Go test that runs `xmllint --noout --nonet --schema` on every golden file when `xmllint` is on the `PATH` (skipped otherwise).
- **D16.** **The XSDs are vendored** (FA(3) plus its base schemas). One patch: the FA(3) schema import (an http URL) is rewritten to a local file so validation works offline with `--nonet`. A test asserts the patch. The schema is embedded in the program for `fv issue --validate`.
- **D17.** **`P_6` is omitted when the sale date equals the issue date**, as the XSD documentation says. The preview always shows the sale date.
- **D18.** **`P_1M`** is written only when `seller.place_of_issue` is set (optional in the XSD).
- **D19.** **`NrRB`.** A Polish IBAN is written as 26 digits (no `PL`, no spaces), matching the White List's account format. A non-Polish IBAN is written in full without spaces. No SWIFT in v1.
- **D30.** **The exchange rate goes in each line's `KursWaluty`**, and `P_14_xW = round half up (P_14_x × mid)`. The table number and date go into `DodatkowyOpis` (key "Kurs waluty", value `1 EUR = 4.2512 PLN, tabela 211/A/NBP/2026 z 2026-10-30`). `KursWalutyZ` is not used (it is for advance invoices).
- **D31.** **`last_day_of_month`** is the last day of the issue date's month. A second value, `last_day_of_previous_month`, covers invoicing early for the previous month. Month template tokens use the sale-date month; `{month_name}` is the Polish nominative in lower case (`październik`).
- **D32.** **`payment_days` defaults to 14.** A due date is always written (`TerminPlatnosci/Termin`) with `FormaPlatnosci=6` and the bank account. A missing bank account is exit 1.

## Process

- **D38.** **Live TEST evidence is out of scope of the build.** The first public version was built against an end-to-end test with a fake KSeF. The later live run against KSeF DEMO is recorded in the README status section.
- **D39.** **The guide's example outputs** in [Workflow](workflow.md) are generated by an in-process transcript test against fakes with a fixed clock; the test fails if the page differs from the real output, and `-update` rewrites it. The config reference is tested against the program in both directions, and every `fv ...` line in the guide parses against the real command tree.

- **D40.** **An import replaces the credential folder atomically, and last.** The new files are written to a sibling folder and checked (key, certificate NIP) first. `fv init` then swaps it in with the previous folder kept aside, stores the passphrase in the keyring, and only then deletes the previous folder. Any failure before that (wrong NIP, keyring refusing the write) puts the previous credential and its passphrase back. No file of an earlier import (a `credential.p12` next to a newer `key.pem`) survives a successful import.
- **D41.** **Ctrl-C.** At an interactive prompt (the `PRODUCTION` confirmation, the `fv init` questions, the passphrase) nothing has been sent, so fv stops at once with exit code 10 and restores terminal echo. Anywhere else the first Ctrl-C cancels the run's context, so a send in flight ends as `sending`/`unknown` through the normal paths (resolve it with `fv status`); a second Ctrl-C kills the process.

## Open

- **Live evidence.** No run against the live KSeF TEST environment, the White List or VIES has been made from the build environment. The instructions for getting a certificate from the KSeF taxpayer application describe the process from MF's published API documentation and may differ in wording from the screens.
- **No code signing**: releases are built in CI with checksums, but the binaries are not signed or notarized ([Install](install.md)).
- **`fv init` on a machine without a keyring** cannot import a certificate (`fv init` fails early and clearly and imports nothing). The workaround is in [Setup](setup.md#where-the-passphrase-lives).
- **Out of v1:** corrections (FA KOR), advance and margin invoices, `0` and `np` rates, split payment and cash accounting, more than one line per invoice, batch sessions, offline modes, PDF with QR code, GUS BIR1, receiving purchase invoices.
